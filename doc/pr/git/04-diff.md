# Diffs

The key ideas behind `diff`:

+ Most digital information can be compared and potentially versioned.
+ Data doesn't usually change quickly relative to its total size. This results in less storage.
+ Scanning for changes pinpoints important aspects of files as they relate to systems & users.
+ Changesets are composable and, with some caveats, can be re-ordered.
+ Even though `diff`'s focus is on change, there needs to be enough similarity for that to be meaningful.

### Why `git init` Before Changing The Template's Code?

At the outset of a new project, especially using a new language or framework, there's often research and googling leading in contradictory directions. Many small boilerchanges seem necessary, but which ones? And which files did they affect?

Git can introduce overhead: working without it may `10x` productivity. Still, a simple `git init` with a single initial commit tracks the changes. It's not good practice to commit deterministically generated build artifacts, but if those files are not in `.gitignore`, then `git status` and `git diff` can be a kind of x-ray vision. This initial `git commit` can't be created afterwards without starting over.

> As an example, the AdvantageKit templates are generated by Github workflows.
> There are five of them in 2026. What distinguishes each template? If they're not
> in `git` until you unzip them and begin, how does `git` help? ... Well, it's faster
> to use `diff -Nur $template1 $template2 > $output`. This can be cumbersome to scan,
> but GUI tools work just as well.

#### Czkawka

Krokiet is the GUI frontend for Czkawka. This tool is especially useful if you need to compare against backups that aren't stored in the cloud. If for some reason, you need a tool like Czkawka/Krokiet and you're not using it, this could save hundreds hours of your time (... or thousands). Czkawka will index files faster than 98% of other tools.

If you primarily back your files up to cloud storage, versions and file de-duplication are managed for you. This is difficult to automate in Linux without some forethought. Syncing cloud storage can add to system I/O, which is mostly an issue when many files change frequently or when many users change the same sets of files.

#### Diffoscope

This is a fairly advanced tool that answers questions like:

+ How did specific types of files change? Zip file? Executable file? `diffoscope` uses other CLI tools to generate text-based output that it compares.
+ Both images or `.tar.gz` contain this executable file -- but which libaries does each version link to? Are these two exactly the same?
+ We loaded this version of Photonvision onto our OrangePi. Now *something* isn't working like it was. Which files changed?

While `diffoscope` won't be the first tool to reach for, it can identify changes in archives quickly.

+ ISO's and Linux disk images are a type of archive format.
+ If it's ISO-9660, it can't be written to by a standard boot -- when Linux boots from this, everything is in RAM.
+ When the Orange Pi is loaded entirely from an SD card where it also stores & modifies files, these disk partitions can be compared against the partitions in the `*.iso` or `*img` file.
+ Either extract the partitions from the disk image, use `losetup` to `mount` files as disks ... or, if bits and bytes are your thing, compare directly in-memory using `dd`.

## `diff` composition

With caveats, changesets are usually composable:

+ Usually: $\Delta_2 \circ \Delta_1 (file)\cong \Delta_1 \circ \Delta_2 (file)$
+ **Sometimes:** $\Delta_1 \circ f \circ (file)\cong f \circ \Delta_1 (file)$

Since applying a `patch` to a fileset is itself a function, the concepts of function composition, commutativity and associativity can be useful. e.g.

+ Data read from a file may be transformed in `csv`, then converted to `json/yaml`
+ Or converted from `csv` to `json/yaml` first, **then** an *equivalent* function may transform it.

For `git`, `diff` and `patch`, most operations are application of changesets.

The specifics depend on the files, context & goal. Usually, when changesets don't overlap, then successive `patch` operations may be composed:

$\Delta_{3,2,1}(file) \cong \Delta_3 \circ \Delta_2 \circ \Delta_1 \circ (file)$

> In some cases, the patches themselves can be meaningfully diffed, sometimes
> called an inter-diff. > Getting this to work well without specific tools is
> complicated.
